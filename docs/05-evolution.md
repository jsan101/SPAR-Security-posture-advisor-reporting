# Evolution

The method went from a two-part deck to a governed practice in about five months. Every version is archived with a dated reason. The direction has been consistent: more context for the client, more of the work made checkable, and open correction when the method was wrong.

---

## Phase 1: A consistent deck (May 2026, v1)

The starting point was consistency. Each client got the same deck with a two-part mission:

1. Tell the client how to reduce noise, with specific console moves from their false-positive clusters.
2. Correlate true positives with active campaigns and turn each into next steps.

There were three files per cycle (deck, document, workbook) and no memory between cycles.

## Phase 2: Memory and the outside view (June 2026, v2.0–v2.4)

- **Outside-in exposure** became a standing section
- **A posture scorecard** with a trend line, and **a persistent memory file per client**, so findings and recommendations carried forward.
- **A client-side-first Action Plan** with owners, timelines, and expected outcomes.
- **MDR escalation outcomes** became the ground truth for containment.
- **A structured export** of every finished deck.
- **Service-tier intake** and client-facing hardening (no internal IDs, notes, or tool names in a deliverable).

**The self-audit.** On June 9 I audited the practice's own output, starting with numbers and then reading for consistency. It found ten defects. The outcome was an automated validator that now gates every delivery.

## Phase 3: A forward view (July 2026, v2.5–v3.2)

- **Horizon:** a 90-day outlook per client, drawn from **ten maintained industry threat profiles**, each with a dated source table and a 45-day refresh rule.
- **Attack chain-stage assessment** against a composite playbook corroborated by public reporting.
- **A deterministic toolkit** so every number comes from code.
- **Continuity modes** so the practice runs with full AI, assisted AI, or no AI.
- **A durability rewrite:** fixed invariants, capability bindings that survive tool and model changes, a failure-mode ledger, and a change protocol with frozen interfaces.
- **Links to the client's own case records** and console alerts, never hand-constructed.
- **Current threat landscape and a software watch list**, where active exploitation outranks CVSS.

## Phase 4: Service health and corrections (August 2026, v4.0–v4.7)

- **Branding update** for every deck.
- **Configuration and health:**
- **Agent lifecycle:** Agent health for a 6 month window
- **Monthly service metrics and response-time adherence** by severity, with any miss stated in words.
- **"Work delivered on your behalf,"** added because a client asked: what was closed without needing them, what hunts ran, what happened lately.
- **Correction:** a blank mitigation field is no longer read as a failure.
- **Correction:** the endpoint-policy baseline was re-aligned
- **An out-of-cycle workflow** for auditing new detection-rule releases against a client's data sources.

## Phase 5: Register, length, and speed (September 2026, v5.0–v6.1)

- **A tone standard:** factual and supportive
- **A content budget** with a defined trim order that moves depth into the written record rather than out of the brief.
- **Model routing:** threat-intelligence judgment goes to a frontier model; drafting and mechanical steps go to a lighter one that may never author an outside-world claim.
- **A new master design** and reading rules for the vendor's updated agent support matrix.
